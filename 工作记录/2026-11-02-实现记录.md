# 2026-11-02 MuMu 实例音频路由 — 实现记录

## 需求

MuMu 模拟器多开两个实例（用户说的"木木实力"就是 MuMu 模拟器）：

- 哪个实例在前台，哪个实例就有声音
- 后台的实例自动把音量关成零
- 切换实例时自动跟随
- **占用要够小**
- **随 MuMu 启动而启动，随 MuMu 关闭而关闭**

用户原本的想法：对 MuMu 管理器做逆向、写插件。

## 结论：不用逆向

用户提出的逆向+插件方案被否掉，理由是实测发现外部就能完全控制，逆向的成本和风险（闭源、升级即失效、注入稳定性）完全不必要。

## 排查过程

### 1. 定位进程结构

快捷方式 → `D:\E\MuMu Player 12\nx_main\MuMuNxMain.exe --from-shortcut`（多开器/管理器）。

运行中进程：

| 进程 | PID | 角色 |
| --- | --- | --- |
| `MuMuNxMain.exe` | 19560 | 多开器 / 管理器 |
| `MuMuNxService.exe` | 21056 | 服务 |
| `MuMuNxSVC.exe` | 25972 | VirtualBox hypervisor 服务 |
| `MuMuNxDevice.exe` | 2044 | 实例「1」窗口 |
| `MuMuNxDevice.exe` | 25504 | 实例「2」窗口 |

**关键**：每个实例是**独立的 `MuMuNxDevice.exe` 进程**，窗口标题就是实例名（"1"/"2"）。

### 2. 确认音频归属（Core Audio 会话枚举）

用 PowerShell + COM（`IMMDeviceEnumerator` → `IAudioSessionManager2` → `IAudioSessionControl2` / `ISimpleAudioVolume`）枚举渲染设备会话，实测：

```
PID=25504  MuMuNxDevice  state=0  vol=1.00  mute=False
PID=2044   MuMuNxDevice  state=1  vol=1.00  mute=False
```

**两个实例是两条独立音频会话，且会话 PID == 窗口 PID**。这是整个方案成立的核心。

### 3. 确认音频后端

`vms\MuMuPlayer-15.0-1\MuMuPlayer-15.0-1.nemu`（VirtualBox 机器描述）：

```xml
<AudioAdapter driver="DirectSound" enabledIn="true" enabledOut="true"/>
```

声音走 VirtualBox 的 DirectSound 后端，在实例进程内输出。改 `enabledOut` 需要重启 VM，不适合实时切换 → 走会话静音。

### 4. 验证 SetMute 可写

对 PID 25504 调 `ISimpleAudioVolume.SetMute(true)` → 读回 `mute=True`；恢复 `false` → 读回 `False`。可写、可读、不影响其他进程。

### 5. 排除 MuMu 原生选项

扫 `MuMuNxDevice.exe`（34MB）字符串：`Mute` 177 处、`Volume` 54 处，均为 VBox 音频代码的 ASCII 符号，没有 UI 级"后台静音"开关。管理器配置 `configs\*.json` 里也没有对应项。

## 实现

C# / .NET Framework 4.8，`csc.exe` 直接编译成 34KB 单文件 exe，无第三方依赖。

### 核心逻辑

1. `SetForegroundWindow` 轮询（100ms）拿前台窗口 → `GetAncestor(GA_ROOT)` 取顶层 → `GetWindowThreadProcessId`
2. `Toolhelp32Snapshot` 建进程树：`MuMuNxDevice` 的每个 PID + 全部后代 = 一个"实例"
3. 前台 PID 落在哪个实例 → 该实例会话 `SetMute(false)`，其余实例 `SetMute(true)`
4. 静音前记录 `(volume, mute)` 原值，恢复时还原
5. 2 秒一次全量对账：兜底实例重启后音频会话重建（新会话会重新静音）
6. 无前台实例 → 全部静音（可配置成保持有声）

### 生命周期

- **启动**：Windows 永久 WMI 订阅（`root\subscription` 下的 `__EventFilter` + `CommandLineEventConsumer` + `__FilterToConsumerBinding`），WQL：
  `SELECT * FROM Win32_ProcessStartTrace WHERE ProcessName = 'MuMuNxMain.exe' OR ProcessName = 'MuMuNxDevice.exe'`
  平时零常驻，MuMu 一启动系统自动拉起工具。
- **退出**：`MuMuNxMain` + `MuMuNxDevice` 全部消失并持续 6 秒 → 恢复全部声音 → 自行退出。
- 从未检测到 MuMu 时给 60 秒宽限（避免手动双击后自己消失）。

### 占用

- 空闲时每 30 秒调 `EmptyWorkingSet`，工作集可压到 1MB 以内
- 私有内存约 22MB（.NET WinForms 基线），CPU 空闲 ≈ 0
- 不跑 MuMu 时工具不存在

## 补充：验证脚本的「前台锁」坑（2026-11-02 17:02）

用 `tools\verify_switch.ps1` 复验时，切到实例 2 后读到的却是「两个都静音」，一开始误以为工具没跟上。

排查：切换后连续采样前台窗口，发现 `SetForegroundWindow` **返回 True 但实际没切成功**——前台在 100ms 内被浏览器（slimjet）/QQ 抢回。

根因是 Windows 的**前台锁**：只有当前台进程、或刚接收过输入、或被用户允许的进程，才能调用 `SetForegroundWindow`。PowerShell 在后台跑，调用会被系统降级成「任务栏闪烁」。

修法（写进 tools\verify_switch.ps1 的思路）：

1. `AttachThreadInput(当前线程, 前台线程, true)` 把输入队列附加上去
2. `keybd_event(VK_MENU, down/up)` 模拟一次 ALT——这是系统认可的「用户操作」，解锁前台权限
3. `SetForegroundWindow` 此时才能真正生效
4. 切完立刻读音频状态（别等），因为用户的其他窗口随时会抢回

用这个手法后验证通过：

```
=== 切到实例2 后立刻读 ===
  PID=25504  state=0 volume=1.00 mute=False   ← 实例2 有声
  PID=2044   state=1 volume=1.00 mute=True    ← 实例1 静音
```

**注意**：这是验证脚本的限制，不是工具的问题。工具只看「当前前台是谁」，真实用户用鼠标点窗口时前台会真正切换，工具 100ms 内跟上。

## 补充：占用与 GC

- 私有内存跑到 4 分钟时从 22.6MB 涨到 31.5MB，怀疑泄漏。复核 Apply 里的 COM 对象均已 `ReleaseComObject`，判断是 .NET Gen0 堆 + 内存池碎片，不是泄漏。
- 处理：空闲（无实例在前台）时每 30 秒 `GC.Collect()` + `WaitForPendingFinalizers()` + `EmptyWorkingSet`。有实例在前台时不干预，保证切换响应。
## 事故：源码被 PowerShell 写成 mojibake（2026-11-02 17:06）

**现象**：给源码插入 `[assembly: AssemblyFileVersion]` 后编译报一片 `CS1010 常量中有换行符` / `CS1056 意外的字符串`，打开文件发现所有中文变成 `褰撳墠瀹炰緥` 这类乱码，而且**连字符串结尾的引号都被吃掉**。

**根因**：用 `Get-Content $f -Raw` 读 → `-replace` → `[System.IO.File]::WriteAllText(..., UTF8Encoding($true))` 写回。读的时候按 GBK 解码了 UTF-8 字节，写回时把这个「假中文」重新编码成 UTF-8。UTF-8 三字节汉字被 GBK 两字节解析，剩下一个孤立字节无法解码被丢弃，所以是**有损的、不可逆**——不是简单改编码就能还原。

**教训（重要，以后写文件一律遵守）**：

- 改含中文的源码/脚本，**不要用 `Get-Content` + `WriteAllText` 做全文读改写**，直接用编辑工具做定点编辑。
- 必须全文改写时，用 `[System.IO.File]::ReadAllText($f, [System.Text.Encoding]::UTF8)` 显式指定 UTF-8 读。

**恢复**：坏文件的中文已不可救，但英文骨架（代码结构、P/Invoke 签名、逻辑流程）完好。按骨架把 10 个类逐段重读，重写整份源码，逻辑原样保留、中文全部重写正确。重写后编译通过（34.5KB），真实切换验证通过：

```
切到实例1 → 200ms 后：PID=2044 mute=False（实例1 出声）、PID=25504 mute=True
```

**备份**：事故期间保留了 `MuMuAudioRouter.exe.bak-working`（v1.1 可运行版）与 `src\MuMuAudioRouter.cs.broken`（坏源码），确认 v1.2 正常后删除。

## 踩过的坑

1. **PowerShell 5.1 + 无 BOM 的 UTF-8 .ps1**：中文被 GBK 解码后破坏字符串引号，报"字符串缺少终止符"。修法：脚本转 UTF-8 BOM，或脚本内只用英文。
2. **Add-Type 的 C# 代码里写中文**：同样被 GBK 解码破坏，编译报"常量中有换行符"。修法：C# 内只用英文，中文放 PowerShell 层。
3. **PowerShell "警告视为错误"**：未使用的变量 `volObj` 导致 Add-Type 编译失败。删掉即可。
4. **.NET Framework 自带 csc.exe 只支持 C# 5**：`?.` 空条件运算符直接报 `CS1525`。改成显式 null 检查。
5. **`$args` 是 PowerShell 自动变量**，不能赋值，改用 `$cscArgs`。
6. **Icon.FromHandle 不接管句柄**：不调 `DestroyIcon` 会泄漏 GDI 句柄；改为 `Clone()` 后销毁原句柄，并把三种状态图标缓存复用。
